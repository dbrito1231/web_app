# Questions tf-g6 (Terraform state) -- implementation report

## What was written

12 questions in `content/questions/q-tf-004-6{a,b,c,d}-{mc,mc2,mr}.json`, generated by a scratchpad script (`g6q_gen.py`) that keeps `id`, `type`, `module`, `difficulty`, `objectiveIds` and rewrites `stem`, `choices`, `correctAnswerIds`, `rationale`, `citationIds`, `mcpStatus: "verified"`, `reviewedOn: "2026-09-26"`, with `selectCount` 1 (MC) or 2 (MR). Fact ownership follows TEACHER-Lg6 "Three facts per objective". Key positions were fixed last and the rationales describe choices by content only (no letters). The `removed` question tests only `lifecycle { destroy = false }` behaviour. Version floors are not tested as keys (1.5 appears only in the 6d-mc2 rationale as context; 1.7 and 1.1 appear nowhere). The one-to-one rule is not used.

Questions to watch for the reviewers (my own judgment of the thinnest points):
- 6d-mc2 distractor `terraform import` once per bucket: wrong for the taught reason that the docs steer to the `import` block and say configuration-driven import "lets you import multiple resources at once, review the import in your plan-and-apply workflow." The lesson does not say the command has no preview (that sentence was dropped as unsupported), so the stem's requirement is phrased as "all twenty in one reviewed plan-and-apply run, with the adoption visible in the plan output", which is the quoted block property.
- 6b-mc2 uses `-lock-timeout` in prose without a value, because the lesson teaches `-lock-timeout=<duration>` and the default 0s but no example duration.
- 6c-mr: the "plain init migrates without prompts" distractor is false on both init pages (one option has to be supplied; Terraform asks).

## Per-question entries and the two-question distractor check

For each distractor: (R) is it a real Terraform option or practice, and (T) is the reason it is wrong taught in `lesson-tf-g6`. All answers are yes to both.

### q-tf-004-6a-mc (fact: no backend block = local backend, `terraform.tfstate` path, `.backup`) key c
- a `path` mandatory: R yes (`path` is a real argument); T yes (6a: `path` is optional and defaults to `terraform.tfstate` relative to the root module).
- b `.terraform` holds state, safe to commit: R yes (a real directory people confuse); T yes (6c: it holds the backend configuration; "Do not check this directory into Git").
- d HCP Terraform is the default: R yes; T yes (6c: HCP Terraform needs a `cloud` block; 6a: no block means local).

### q-tf-004-6a-mc2 (fact: what local state lacks) key a
- b default takes no lock: R yes (a common belief); T yes (6a: the local backend "locks that state using system APIs").
- c only default workspace: R yes (workspaces exist); T yes (6a: `workspace_dir` and the named-workspaces gloss).
- d commit state to Git: R yes (real practice); T yes (Warnings: version control "can result in data loss or exposure of secrets"; 6a: the local file limits collaboration).

### q-tf-004-6a-mr (facts: legacy flags; migrating back) keys a, d
- b flags recommended: R yes; T yes (6a: no longer recommended; the recommended replacement is a remote backend).
- c flags override under S3: R yes; T yes (6a: "no effect for configurations that have a different backend type selected").
- e removal discards state: R yes (a plausible reading of "back to local"); T yes (6a: Terraform prompts to migrate the state to the default local backend).

### q-tf-004-6b-mc (fact: automatic, backend-dependent locking) key d
- a only with `-lock=true`: R yes (`-lock` is a real flag); T yes (6b: automatic; `-lock=false` is how it is disabled).
- b every backend locks: R yes; T yes (6b: "Not all backends support locking").
- c apply only: R yes; T yes (6b: "all operations that could write state"; state-modifying commands accept `-lock=false` and `-lock-timeout`).

### q-tf-004-6b-mc2 (fact: `-lock-timeout` versus `-lock=false`) key b
- a local backend: R yes; T yes (the stem requires shared state; 6a: a local file sits on one machine and is not shared).
- c `-lock-timeout=0s` waits forever: R yes (a valid flag with a real default); T yes (6b: default 0s "causes immediate failure").
- d `-lock=false`: R yes; T yes (6b: not recommended, dangerous with concurrent users).

### q-tf-004-6b-mr (facts: `force-unlock`; S3 `use_lockfile` versus DynamoDB) keys b, e
- a DynamoDB arguments removed: R yes (DynamoDB locking is a real, deprecated method); T yes (6b: "will be removed in a future minor version"; both can be configured simultaneously).
- c S3 locks by default: R yes; T yes (6b: opt-in, `use_lockfile` defaults to false).
- d `force-unlock` safe for anyone: R yes; T yes (6b: only for your own lock after automatic unlocking failed; "multiple writers").

### q-tf-004-6c-mc (facts: backend block limits; `backend` versus `cloud`) key a
- b variables allowed: R yes; T yes (6c: cannot refer to named values, including input variables).
- c one backend per environment: R yes; T yes (6c: only one backend block).
- d cloud beside backend: R yes; T yes (6c: mutually exclusive).

### q-tf-004-6c-mc2 (fact: partial configuration, `-backend-config`, credentials) key d
- a hardcode credentials: R yes; T yes (6c: hardcoded and `-backend-config` values both land in `.terraform` and plan files).
- b skip the block: R yes; T yes (6c: an empty block naming the type is the minimum).
- c commit `.terraform`: R yes; T yes (6c: "Do not check this directory into Git").

### q-tf-004-6c-mr (facts: `-migrate-state`, `-reconfigure`, `-force-copy`) keys c, d
- a `-reconfigure` copies state: R yes; T yes (6c: it "disregards any existing configuration, preventing migration").
- b plain init migrates without prompts: R yes; T yes (6c: init is re-run with `-reconfigure` or `-migrate-state`; Terraform asks about migrating).
- e backup unnecessary: R yes; T yes (6c: "we strongly recommend manually backing up your state").

### q-tf-004-6d-mc (facts: refresh-only versus a normal apply; `refresh` deprecation) key b
- a plain `apply`: R yes; T yes (6d: would "attempt to revert your manual changes").
- c `terraform refresh`: R yes; T yes (6d: deprecated alias with `-auto-approve`, overwrites state with no review).
- d `plan -refresh-only` alone: R yes; T yes (6d: apply is how you accept it and record it in state).

### q-tf-004-6d-mc2 (fact: `import` block versus command) key c
- a resource blocks only: R yes; T yes (6d: adoption needs an `import` block and the ID; otherwise plan creates new objects).
- b `moved` block: R yes; T yes (6d: `moved` renames an address that already exists in state).
- d `terraform import` per bucket: R yes; T yes in the scoped sense described under "Questions to watch".

### q-tf-004-6d-mr (facts: rename versus forget; no hand edits) keys a, c
- b rename alone keeps the instance: R yes; T yes (6d: Terraform "interprets a change as an instruction to destroy ... and create").
- d `state rm` destroys the real database: R yes; T yes (6d: it removes the binding "without first destroying it").
- e hand-edit state JSON: R yes (people do it); T yes (6d: "Do not directly edit this file"; state commands exist; backups).

## Facts plan per objective (supports all 20 questions)

Each objective has 5 questions: mc, mc2, mr (two correct) plus two extra MCs. Every objective has at least six distinct facts, so none is thin. No fact is assigned to two questions; the mr uses two of the facts marked MR.

- 8a Use HCP Terraform to create infrastructure
  - mc: remote operations run on HCP Terraform's own disposable VMs; a CLI `terraform apply` in a remote workspace executes there, output streamed.
  - mc2: three workflows: UI/VCS-driven (primary, commits start runs), CLI-driven, API-driven (workspace not tied to a repo; your tooling uploads a `.tar.gz`; HCP Terraform does not fetch from VCS).
  - mr (MR facts): a VCS workspace run starts when commits merge to the linked branch; a pull request starts a speculative plan; remote `terraform apply` is for workspaces without a linked repository.
  - extra-00: speculative plans are plan-only and cannot apply; fork pull requests do not start them.
  - extra-04: HCP Terraform always plans first and by default waits for approval; a no-change plan ends "Planned and finished"; each workspace has its own run queue with pending runs.
  - spare: `terraform import` is not executed remotely; saved plans need CLI v1.6.0; the run stage list.
- 8b Describe HCP Terraform collaboration and governance features
  - mc: the Plan role proposes (queues plans) but cannot apply; the Write role applies; permissions are additive and the highest wins.
  - mc2: Sentinel versus OPA: Sentinel imports (`tfplan`, `tfconfig`, `tfstate`, `tfrun`), OPA Rego query returning an empty array to pass; one framework per policy set.
  - mr (MR facts): Sentinel levels advisory, soft mandatory, hard mandatory; OPA has only advisory and mandatory, and mandatory is overridable by a user with Manage Policy Overrides; hard mandatory is not overridable unless the policy set allows overrides.
  - extra-01: run tasks send run data to an external service at pre-plan, post-plan, pre-apply or post-apply; advisory versus mandatory; the most restrictive level wins.
  - extra-05: use one of: cost estimation off by default and shown between plan and apply; health assessments (drift detection, continuous validation) need Standard or Premium and Remote or Agent mode; audit trails keep 14 days and need Standard or Premium; the private registry shares modules and providers inside the organization.
  - spare: team management needs Essentials, Standard or Premium; the free edition has one policy set of up to five policies.
- 8c Describe how to organize and use HCP Terraform workspaces and projects
  - mc: HCP Terraform workspaces are required and hold configuration, variables, state and permissions; CLI workspaces are optional extra states in one directory.
  - mc2: projects group workspaces, each workspace is in exactly one project, the Default Project cannot be deleted, project permissions need a paid edition.
  - mr (MR facts): execution mode Local (state only; workspace variables and variable sets not evaluated); Agent (private infrastructure, paid); Remote (disposable VMs, enables Sentinel and cost estimation).
  - extra-02: remote state sharing is off by default; options organization, project, specific workspaces; `tfe_outputs` is recommended and ignores the access controls.
  - extra-06: variables: Terraform versus environment variables, sensitive is write-only but can still reach logs and state, variable set scopes (workspace, project, global), workspace-specific beats variable sets.
  - spare: run triggers (up to 20 source workspaces, admin access, no auto-apply by default); workspace lock keeps runs pending; the recommendation to split large configurations.
- 8d Configure and use HCP Terraform integration
  - mc: `terraform login` stores the token in plain text in `credentials.tfrc.json`, defaults to app.terraform.io, interactive only.
  - mc2: `cloud` block: `workspaces` takes `name` or `tags` (mutually exclusive); `name` ties the directory to one workspace and the CLI cannot manage it; `tags` matches all tags and new workspaces inherit them.
  - mr (MR facts): `TF_CLOUD_ORGANIZATION`, `TF_CLOUD_PROJECT` and `TF_CLOUD_HOSTNAME` apply only when the argument is omitted (the configuration wins) and an empty `cloud` block is still needed; `TF_WORKSPACE` selects an existing workspace and never creates one.
  - extra-03: `terraform init` after adding or changing the block migrates existing state and may prompt for renaming; swap `backend "remote"` for `cloud`; `prefix` is unsupported, use `tags`.
  - extra-07: VCS integration: OAuth, webhooks, one branch per workspace, specific directories can trigger runs, a connection can be scoped to projects, module tags publish private modules.
  - spare: implicit workspace creation on init and its defaults; `.terraformignore`; the `cloud` block needs Terraform 1.1 or later.

Overlap risks for the question writer: 8b Sentinel levels (mr) and run task levels (extra-01) are both advisory/mandatory lists; the lesson states both and says run task levels are not the policy levels, so a question may separate them. 8a extra-04 (queue and approval) and 8c Remote mode (where runs execute) are different facts.
